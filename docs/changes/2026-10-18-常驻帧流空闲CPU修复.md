# 常驻帧流导致的空闲 CPU 占用

日期：2026-10-18

## 现象

Index 空闲（仅菜单栏，无窗口、无截图）时：

- `Index` 进程 CPU 16–32%；
- `replayd` 2–3%；
- `WindowServer` 82–90%（退出 Index 后回落到 ~37%，即系统基线）。

四块屏：内置 3024×1964、4K 3840×2160、竖屏 1440×2560、3360×1890。

## 根因

`ScreenFrameStreamer` 在 App 启动时对每块屏建一条 30fps SCStream，并在每帧回调里：

```swift
let pixelData = Data(bytes: basePtr, count: bytesPerRow * h)  // 整屏 memcpy
```

四块屏约 97MB/帧；即使没有订阅者（overlay 用冻结帧，`subscribe` 全仓无调用），
每帧仍要拷贝、建 `CGImage`、再派发一个主线程 `Task`。采样显示
`ScreenFrameStreamer.swift:346` 占帧流队列 27% 的采样时间。

同时，四条常驻流让 WindowServer 持续合成，App 自身修好后系统仍有 ~45% 的额外负载。

## 修复

1. **零拷贝缓存**：`FrameStore` 改存 `CVPixelBuffer`，收帧只 retain；`CGImage`
   只在 `snapshots` / 有订阅者时转换。无订阅者时不再派发主线程 Task。
2. **按需启停**：App 启动不建流；首次截图走 `SCScreenshotManager` 慢路径，
   成功后后台预热；每次截图顺延 `scheduleIdleStop(after: 20)`，20 秒无截图自动停流。
3. **防重入**：主动 `stop()` 期间 `handleStreamStopped` 不再触发重建；
   teardown 不会变成重建回环。
4. 测试：`FrameStore` 断言改为 `CVPixelBuffer` 尺寸；新增
   `makeImage(from:)` 转换测试（603 tests）。

## 实测

| 指标 | 修复前 | 修复后（空闲，未截图） |
|---|---|---|
| Index CPU | 16–32% | **0.0%** |
| replayd | 2–3% | **0.0%** |
| WindowServer | 82–90% | **37.8%**（= 退出 Index 的基线） |

采样中 `makeImage` / `Data(bytes:)` 命中为 0。

## 代价与待验证

- 空闲后的第一张截图走慢路径（SCScreenshotManager），之后 20 秒内再截图走快路径。
- 截图后的 20 秒预热窗口内，WindowServer 会短暂回到较高占用；若不需要快路径，
  可以去掉 `MacScreenCapturer` 里的预热 Task。
- 真实截图、选区冻结与标注需手动验证一次。
